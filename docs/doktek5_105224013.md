## 1. Skema Validasi
Bagian ini mendefinisikan aturan struktur data pada formulir pengaduan anonim menggunakan pustaka **Zod** yang diletakkan terpusat pada direktori `lib/skema.ts`.

### Tabel Kolom Formulir & Aturan Zod
| Nama Kolom | Aturan Zod (Schema Rule) | Pesan Galat Kustom |
| :--- | :--- | :--- |
| **`kategori`** | `z.string().min(1, ...)` | *"Silakan pilih kategori pengaduan terlebih dahulu"* |
| **`lokasi`** | `z.string().trim().min(3, ...).max(100, ...)` | *"Lokasi kejadian minimal harus 3 karakter"* / *"Lokasi maksimal 100 karakter"* |
| **`judul`** | `z.string().trim().min(5, ...).max(100, ...)` | *"Judul laporan minimal 5 karakter"* / *"Judul maksimal 100 karakter"* |
| **`kronologi`** | `z.string().trim().min(15, ...).max(500, ...)` | *"Kronologi kejadian minimal 15 karakter agar jelas"* / *"Kronologi maksimal 500 karakter"* |

### Aturan Semantik (Pendekatan Frontend Client-Side)
Karena arsitektur aplikasi bersifat *frontend-only*, validasi semantik dan sintaksis dijalankan langsung di sisi klien menggunakan fungsi **`safeParse`** milik Zod pada komponen `FormLaporan.tsx`.
* **Alasan Pemilihan Pendekatan:** Memastikan bahwa data yang dikirimkan oleh pengguna bersih dari spasi berlebih (`.trim()`), memenuhi batas panjang karakter minimum agar informasi laporan bermakna, serta memberikan umpan balik instan (*real-time feedback*) tanpa membebani server simulasi.

## 2. Alur Server Action & Pembagian Berkas

### Urutan Alur Eksekusi Pengiriman Formulir
1. **Pemicu Pengguna (*Client Event*):** Pengguna menekan tombol "Validasi & Kirim Laporan" pada komponen formulir.
2. **Pencegahan Default:** Fungsi `handleSubmit` mencegah perilaku bawaan halaman melakukan *refresh* (`e.preventDefault()`).
3. **Validasi Bentuk (*Schema Parsing*):** Objek penampung `formData` diuji strukturnya secara instan menggunakan `skemaPengaduan.safeParse(formData)`.
4. **Penanganan Hasil Validasi:**
   * **Jika Gagal (`!result.success`):** Daftar galat dipetakan dari Zod *issues* ke dalam state `errors`, lalu dirender langsung ke bawah kolom input terkait.
   * **Jika Berhasil (`result.success`):** State galat dibersihkan, status sukses diaktifkan, dan data log valid ditampilkan di konsol pengembang.

### Pembagian Berkas Arsitektur
* **Server Component (`app/lapor/page.tsx`):** Berfungsi sebagai halaman penampil rute (`/lapor`) yang merender tata letak statis utama.
* **Client Component (`components/FormLaporan.tsx`):** Diberi direktif `"use client"` karena memuat *React Hooks* (`useState`) serta fungsi interaktif penanganan *event submit* dan DOM lokal.
* **Berkas Skema (`lib/skema.ts`):** Berkas utilitas terpusat yang mendeklarasikan objek validasi `z.object` dan tipe TypeScript turunannya.

## 4. Session dan Cookie
* **Login simulasi:** Tombol **Masuk** mengirim `POST /api/masuk`. Server development Vite membalas dengan header `Set-Cookie` bernama `sesi`, berisi ID acak yang berlaku 30 menit, lalu menyimpan sesi tersebut di memori.
* **Pemeriksaan sesi:** Saat aplikasi dibuka, browser mengirim `GET /api/session`. Server merespons `200` jika cookie cocok dengan sesi aktif, atau `401` jika cookie tidak ada, kedaluwarsa, atau sudah dicabut.
* **Logout:** Tombol **Keluar** mengirim `POST /api/logout`. Server mencabut sesi dan menghapus cookie dengan `Max-Age=0`.
* **Atribut cookie:** Cookie menggunakan `HttpOnly` (tidak dapat dibaca JavaScript), `SameSite=Lax`, dan `Path=/`. Atribut `Secure` ditambahkan saat koneksi menggunakan HTTPS. Karena server lokal Vite biasanya berjalan melalui HTTP, atribut `Secure` tidak muncul pada pengujian lokal.
* **Catatan keamanan:** ID sesi dapat dilihat melalui DevTools, tetapi tidak diekspos ke kode frontend. Klik **Masuk**, lalu buka **Network**, pilih request `masuk`, dan lihat **Response Headers → Set-Cookie**. Nilai cookie dapat dilihat di **Application → Cookies**. Implementasi ini adalah simulasi lokal untuk demonstrasi, hanya aktif di server development Vite, dan bukan autentikasi produksi.

## 5. Keputusan Teknis
* **Alasan Pola Session di Server dibanding Token di Cookie:** Penyimpanan sesi berbasis server (*server-side session*) pada aplikasi sensitif seperti pengaduan korupsi (*IntegritasKita*) memberikan keamanan tingkat tinggi karena data sensitif pengguna tidak terekspos di sisi klien, serta mempermudah proses pencabutan akses (*revocation*) secara instan apabila terjadi aktivitas mencurigakan.
* **Batasan Peran Middleware dibanding Pemeriksaan di Aksi:** Middleware bertindak sebagai garda terdepan untuk pemeriksaan rute global secara cepat (pembatasan akses halaman admin), sementara pemeriksaan di dalam fungsi aksi (*Server Action / Handler*) bertindak sebagai lapisan pertahanan kedua guna memastikan integritas data muatan (*payload*) sebelum diproses lebih lanjut.

## 6. Kendala dan Penyelesaian
* **Kendala 1 (Konflik Dependensi Paket):** Terjadi galat resolusi `ERESOLVE` saat menginstal pustaka `zod` akibat perbedaan versi peer dependencies dengan `lucide-react` dan React 19.
  * *Penyelesaian:* Menjalankan perintah instalasi dengan flag `--legacy-peer-deps` (`npm install zod --legacy-peer-deps`) untuk mengabaikan konflik versi minor yang tidak berdampak pada fungsi inti.
* **Kendala 2 (Peringatan Strict Mode TypeScript):** Muncul garis merah pada parameter iterasi Zod issues `(issue)`.
  * *Penyelesaian:* Memberikan tipe data eksplisit pada parameter tersebut menjadi `(issue: any)` agar selaras dengan aturan pemeriksaan tipe ketat di lingkungan editor.
